## Route-by-route trust and replay assessment

Every entry file v2 route entry point (line 4) calls `serveV2` with a fixed literal (no caller-selected dispatch). `server.ts:62` extracts a Bearer token and returns only verified `sub`; [packages/auth/src/index.ts:219](../packages/auth/src/index.ts#L219) pins HS256/audience/required claims. `server.ts:23` uses a nonpersistent service-role client: RLS is bypassed there, so player ownership predicates in SQL matter. CONFIRMED by source and existing JWT/SQL tests; the new boundary test also supplies a forged body player/reward and observes the authenticated identity. JWT wallet claims do not choose the voucher recipient: SQL loads the wallet attached to the player's row.

In the table, SQL references abbreviate `supabase/migrations/20261101000000_v2_cat_rpg.sql`; Edge references abbreviate `supabase/functions/_shared/v2/`. “Replay safe” means no duplicate payout for the same consumed resource/window, not a durable cached HTTP response.

Full claim/boss consistency *does* require equipment in the shared revision. PGlite executes statements on one connection; the route barrier makes two readers see the same state before competing CAS, but does not reproduce multi-connection row-lock wait behavior, real deadlocks or distributed isolate scheduling. Those remain NOT VERIFIED on production PostgreSQL.

## Voucher path: issuance → signature → mint

- **CONFIRMED, no body-selected recipient or unowned entitlement:** Edge `forge.ts:89` derives the relic rarity/id, SQL line 617 locks the authenticated player, line 641 spends owned stacks, and SQL voucher JSON [supabase/migrations/20260106000000_relic_forge.sql:38](../supabase/migrations/20260106000000_relic_forge.sql#L38) fetches that player's stored wallet. No `itemId`, `player`, `relicId`, rarity, nonce, expiry or signature body field enters this path. With no arbitrary-item-conversion API there is no separate “gear to be owned” to forge; the paid forge row is the entitlement.
- **CONFIRMED stable, unique nonce:** [supabase/migrations/20260101000000_init_schema.sql:53](../supabase/migrations/20260101000000_init_schema.sql#L53) is a bigint identity primary key; JSON exports it as a decimal string, signed with BigInt (`voucher.ts:14`), never an imprecise JS nonce number. Player/day uniqueness and issued-per-forge uniqueness are at `20260106000000_relic_forge.sql:14` and line 29. Normal parallel forge/retry and different-player uniqueness pass; existing expiry-reissue tests preserve same Relic but change nonce. Sequence reset/redeploy database reuse with the same contract is NOT VERIFIED and must never be assumed safe operationally.
- **CONFIRMED EIP-712 scope:** [supabase/functions/_shared/relic.ts:33](../supabase/functions/_shared/relic.ts#L33) fixes name/version/Fuji chainId/verifyingContract; `voucher.ts:14` signs player/id/rarity/nonce/expiry from DB. Existing migrated forge tests verify a real generated-key signature. Contract `RelicNFT.sol:71` binds caller, line 73 refuses used nonce, line 78 sets used before the ERC-1155 hook, line 94 hashes the domain. Cross-chain/contract replay and double mint are NOT REPRODUCIBLE from the source/current contract tests; no live mint was attempted and Foundry was not run in S2.
- **CONFIRMED concurrent signing semantics:** two callers can both sign the same unsigned row, but the configured local viem signer deterministically produces the same signature/fields/nonce; one paid forge and one voucher row result. “One voucher” does not mean “only one invocation of sign”. Persistence has player+nonce+issued checks (`20260106000000_relic_forge.sql:165`).
- **NOT VERIFIED finality/deployment:** RPC correctness, canonicality after the 120-second grace, confirmations, signer/contract address matching deployed bytecode and real wallet operation. A stale false used-nonce read before reissue is not ruled out by local tests. Current helper `relic.ts:108` checks a receipt/event correctly for mint reporting, but the expired-forge used-bit path does not use it.
