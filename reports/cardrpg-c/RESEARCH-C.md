## Runtime and asset boundary

Choose official `@esotericsoftware/spine-threejs` 4.2.120, pinned, inside the existing Three r180 battle adapter with an orthographic camera. WebGL would duplicate camera/resource/anchor plumbing; Pixi would add another renderer and migration cost without a demonstrated benefit. Keep the existing actor/event interface. Spine Canvas lacks production mesh/clipping support, so it cannot represent the designer's weighted meshes. The official 4.2 README is stale about tint-black: the newer [Three runtime announcement](https://us.esotericsoftware.com/blog/spine-threejs-runtime-update) and current 4.2 source implement it. Verify the pinned package against r180 in C3 rather than treating the older r171 announcement as an r180 guarantee.

Cache stateless SkeletonData/atlas per asset revision; each actor owns its Skeleton and AnimationState. Default mix0.15s, bounded0.1–0.2s, action track entries reuse the runtime pool. Resolve animation names, bones and recipes at load, not each cast. The [official animation guide](https://esotericsoftware.com/spine-applying-animations) documents mixing, per-skeleton state and listeners. Adapt presentation progress to authored clips without changing deterministic battle outcomes. Event crossings dispatch once per action even atx3; a missing event uses the contract's timed fallback and produces a warning.

PMA must be consistent from PNG to GPU: the pinned ThreeJsTexture constructor requests upload premultiplication only for straight-alpha input. Do not multiply an already-PMA atlas twice. Use atlas `pma:true`, linear filtering, clamp,2–4px gutters and<=2048pages. Keep original painted colors with unlit materials, controlled transparent draw order and a small zOffset; test edges over both light and dark backgrounds. Sources: [4.2 ThreeJsTexture](https://github.com/EsotericSoftware/spine-runtimes/blob/4.2/spine-ts/spine-threejs/src/ThreeJsTexture.ts), [texture packing](https://esotericsoftware.com/spine-texture-packer).
