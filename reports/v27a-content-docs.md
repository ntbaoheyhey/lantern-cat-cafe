## 2. TypeScript Runner Architecture & Choices

### Why Vitest was Chosen
The prompt instructed:
> Use whatever TypeScript runner the repo already has (check package.json files and node_modules/.bin; vitest is available) and add no dependency. If plain node cannot import the .ts files, make the script a vitest test file instead at packages/game-rules/src/v2/content/docs.gen.test.ts that writes the file when UPDATE_DOCS=1 and otherwise fails if docs/content-v2.md is out of date. Choose the simplest option that works and explain it in the report.

When attempting plain `node -e "import('./packages/game-rules/src/v2/content/index.ts')"` in Node v26.11.1:
```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../packages/game-rules/src/v2/content/stats' imported from .../packages/game-rules/src/v2/content/index.ts
```
Plain Node ESM cannot resolve extensionless relative imports (`from './stats'`) without custom experimental loaders or bundle steps.

Rather than introducing custom loader scripts or external dependencies, `packages/game-rules/src/v2/content/docs.gen.test.ts` with `vitest` was selected because:
1. `vitest` is already installed in `packages/game-rules` (`vitest@5.0.5`) and configured in `package.json`.
2. It handles TypeScript and ESM resolution natively with zero configuration.
3. Placing the generation logic in a test file (`docs.gen.test.ts`) provides continuous integration protection: `pnpm test` automatically verifies `docs/content-v2.md` matches the code registry, immediately alerting developers if content is modified without updating docs.
4. `scripts/gen-content-docs.mjs` was provided as a thin executable script running `vitest run src/v2/content/docs.gen.test.ts` with `UPDATE_DOCS=1`, allowing developers to simply run `node scripts/gen-content-docs.mjs` to regenerate the documentation.
