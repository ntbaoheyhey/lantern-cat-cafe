## 4. Findings List (Ordered by Impact)

### FINDING #1: Modal dialogs do not return focus to trigger on close (Blocks keyboard use)
- **Component**: `ChestReveal` and `WelcomeBack`
- **File & Lines**:
  - `apps/web/src/layout/loot/ChestReveal.tsx:113-115, 120-124`
  - `apps/web/src/layout/loot/WelcomeBack.tsx:40-42, 47-51`
- **What a keyboard or screen-reader user experiences**:
  When opening either modal, focus correctly lands inside the dialog on its action button (`buttonRef.current?.focus()`). However, neither dialog records the previously focused element (`document.activeElement`) prior to open, and neither dialog restores focus when closed (via Escape, clicking "Collect", or clicking "OK"). Upon unmount, focus drops to `document.body`. Keyboard and screen reader users lose their position in the application layout and must re-tab through the entire page.
- **Exact assertion that failed**:
  ```ts
  const trigger = document.createElement('button');
  document.body.appendChild(trigger);
  trigger.focus();
  const { unmount } = render(<ChestReveal chest={sampleLootV2()} firstClear={false} onDone={vi.fn()} />);
  unmount();
  expect(document.activeElement).toBe(trigger); // AssertionError: expected <body> to be <button>
  ```
- **Suggested fix in one line**:
  Store `const priorFocused = useRef<HTMLElement | null>(document.activeElement as HTMLElement)` on mount and invoke `priorFocused.current?.focus()` during cleanup/closure.

### FINDING #2: BossGatePanel ignores `state.progress.gated` and omits `neededPower` (Confusing)
- **Component**: `BossGatePanel` (and `bossGate.ts`)
- **File & Lines**:
  - `apps/web/src/layout/boss/BossGatePanel.tsx:87-112`
  - `apps/web/src/layout/boss/bossGate.ts:21-78`
- **What a keyboard or screen-reader user experiences**:
  When idle farming is gated by required boss combat power (`state.progress.gated === true` with `state.progress.neededPower > 0`), `BossGatePanel` never inspects `state.progress.gated` or renders `state.progress.neededPower`. If the player reached round 10 kills 6 with at least one key, `bossGateStatus` marks the fight as `ready` (Fight button enabled) rather than explaining that the cat is gated and showing the power threshold required to proceed. Screen reader and keyboard users receive no indication of why idle progress stopped or what stat increase is necessary.
- **Exact assertion that failed**:
  ```ts
  const state = sampleServerStateV2({ chapter: 1, round: 10, kills: 6, gated: true, neededPower: 1500 });
  render(<BossGatePanel state={state} chapter={1} nowS={1000} busy={false} onFight={vi.fn()} onSelectChapter={vi.fn()} />);
  expect(screen.getByText(/1,?500/)).toBeInTheDocument(); // TestingLibraryElementError: Unable to find an element with text: /1,?500/
  ```
- **Suggested fix in one line**:
  Add a `'gated'` case to `bossGateStatus` when `state.progress.gated && state.progress.chapter === chapter` that disables the fight action and renders `Power required: ${state.progress.neededPower}`.

### FINDING #3: ClassPicker and Forge confirmation boxes lack reduced-motion CSS overrides (Cosmetic)
- **Component**: `ClassPicker` and `ForgePanel`
- **File & Lines**:
  - `apps/web/src/layout/classpicker/ClassPicker.css:351, 395-404`
  - `apps/web/src/layout/forge/ForgePanel.css:379, 382-391`
- **What a keyboard or screen-reader user experiences**:
  `.class-picker__confirm-box` specifies `animation: picker-fade-in 120ms ease-out` and `.forge-confirm-box` specifies `animation: forge-pop 140ms ease-out`. While React code does not attach dynamic motion classes, neither stylesheet includes a `@media (prefers-reduced-motion: reduce)` block (in contrast to `loot.css` and `boss.css`). Users with vestibular motion preferences will still observe scaling/translation pop animations when triggering in-panel confirmations.
- **Exact assertion that failed**:
  `@media (prefers-reduced-motion: reduce)` override neutralizing `animation` on `.class-picker__confirm-box` and `.forge-confirm-box` is absent in `ClassPicker.css` and `ForgePanel.css`.
- **Suggested fix in one line**:
  Add `@media (prefers-reduced-motion: reduce) { .class-picker__confirm-box, .forge-confirm-box { animation: none !important; } }`.

## 6. Anything Unsure

1. **Heading Structure in ForgePanel**:
   `ForgePanel` starts its internal headings at level 3 (`h3` for preview name and `Daily Relic Forge`, `h4` for cost list). When embedded in the main shell beneath an `h2` ("Forge"), this conforms to WCAG heading nesting. When rendered in isolation, there is no `h1` or `h2` inside the component boundary itself. We marked this as passing because there are no skipped levels within the component's rendered tree (`h3` -> `h4`).
2. **Focus Return Implementation**:
   Because `ChestReveal` and `WelcomeBack` can be conditionally mounted and unmounted by parent components rather than managing their own internal open/closed state, returning focus reliably requires the components to capture `document.activeElement` on initial mount and restore it in the unmount cleanup function.
